# ADR-004: Stateless Role-Based Access Control (RBAC) via Signed HS256 JWT Middleware

**Date:** 2026-11-08  
**Status:** accepted

## Context

The K-8 School Information System serves four distinct user roles (`student`, `teacher`, `parent`, `admin`) across a decoupled Next.js 16 frontend (`http://localhost:3000`) and Go Fiber v3 REST API (`http://localhost:6769`). Early prototypes passed user identity and role metadata via client-side state or unverified HTTP headers (such as `X-User-Role`). During our security and AI code critique review, we identified two critical risks:

1. **Privilege Escalation via Header Spoofing:** Trusting a raw `X-User-Role: admin` request header allows any unauthenticated client or non-admin user to invoke administrative endpoints (`/api/admin/*`) simply by forging an HTTP header.
2. **Cross-Origin Session Management:** Because the Next.js Presentation tier and Go Fiber Service tier run as separate containers/processes on different ports, cookie-based server sessions require sticky session state and complex CSRF choreography, whereas stateless signed tokens integrate cleanly with REST API calls and unit test suites.

## Decision

Adopt **Stateless Role-Based Access Control (RBAC)** using **HMAC-SHA256 (HS256) JSON Web Tokens (JWT)** signed with `JWT_SECRET` and enforced at both the Service and Presentation tiers:

1. **Token Issuance (`POST /api/login/` in `backend/auth/signIn.go`):** After verifying credentials against `public.users.password_hash` via the domain method `User.VerifyPassword(password)` (`bcrypt.CompareHashAndPassword`), the Service tier mints a signed HS256 JWT embedding claims `id` (school User ID), `role` (`student`, `teacher`, `parent`, `admin`), and `exp` (72-hour expiration).
2. **Server-Side Middleware Enforcement (`backend/auth/middleware.go` & `backend/admin/handlers.go`):**
   - `RequiredLogin()` and `RequiredRoles(allowedRoles ...string)` in `backend/auth/middleware.go` parse and verify the `Authorization: Bearer <token>` signature against `JWT_SECRET` and populate `c.Locals("userID")` and `c.Locals("userRole")`.
   - `AdminRoleMiddleware()` in `backend/admin/handlers.go` protects all `/api/admin/*` routes, rejecting requests without a valid signed Bearer token (`401 Unauthorized`) or with a non-admin role claim (`403 Forbidden`), and explicitly ignoring client-supplied `X-User-Role` headers.
3. **Client-Side Guard Decorators (`frontend/components/auth-guard.tsx`, `frontend/components/role-guard.tsx`, `frontend/contexts/AuthContext.tsx`):** The Next.js frontend wraps routes in `AuthGuard` and `RoleGuard` to prevent unauthorized UI navigation (such as hiding classroom attendance records from students while allowing teachers, parents, and admins) and attaches `Authorization: Bearer <token>` to API requests.

## Consequences

- **Positives:**
  - **Tamper-Proof Role Enforcement:** Clients cannot escalate privileges by modifying `localStorage` or forging `X-User-Role` headers because every protected endpoint verifies the cryptographic HMAC signature using the server-only `JWT_SECRET`.
  - **Stateless Scalability & Testability:** The Go Fiber backend does not need a shared Redis session store, and HTTP handler unit tests (`backend/admin/admin_test.go`) can deterministically test `401 Unauthorized`, `403 Forbidden`, and `200 OK` paths by minting test JWTs.
- **Trade-offs:**
  - Requires `JWT_SECRET` to be configured consistently in the backend `.env` environment (documented in `.env.example` and `README.md`).
