# ADR-002: Data Storage Choice — Adopting Supabase for Managed PostgreSQL and Cloud Storage

**Date:** 2026-10-12  
**Status:** accepted

## Context

In our initial architecture design (ADR-001), PostgreSQL was selected as the relational database engine for the Data Tier. Initially, this was envisioned as a local or directly managed PostgreSQL instance. However, as active development began across the team and CI pipelines, several constraints and operational challenges emerged:

1. **Environment Setup & Team Parity:** Requiring every team member (and automated CI test runners) to install, configure, migrate, and run a local PostgreSQL daemon introduced environment drift and onboarding friction.
2. **Assignment File Storage Requirements:** The School Information System (SIS) requires teachers to attach assignment files (PDFs, prompts) and students to submit homework documents. Storing raw binary files directly inside relational tables degrades database performance and complicates backups, while setting up an independent Amazon S3 bucket added unnecessary configuration overhead for a semester project.
3. **Admin Inspection & Prototyping Speed:** Rapidly testing database records across roles (students, teachers, admins, parents) required an accessible, visual database management dashboard to inspect and verify relational records without requiring local GUI tools (like pgAdmin or DBeaver) on every workstation.

## Decision

Adopt **Supabase** as the project's primary data storage provider for the Data Tier:

1. **Managed PostgreSQL Engine:** Use Supabase's hosted PostgreSQL database as our relational store. The Go backend connects directly using `github.com/jackc/pgx/v5/pgxpool` via standard connection string (`SUPABASE_CONNECTION_STRING`).
2. **Relational Integrity & Native SQL:** Retain pure PostgreSQL schema definitions, foreign keys, cascading deletes, UUID generation (`gen_random_uuid()`), and `JSONB` columns for structured question/answer data (`init_assignments.sql`). We do not rely on proprietary Supabase client libraries for backend data access; all Go handlers execute standard SQL queries.
3. **Object Storage for Assignments:** Leverage Supabase Storage buckets to host assignment documents and student file submissions, persisting the public or authenticated URLs inside the `assignments.file` column.
4. **Shared Cloud Instance:** Use a single, hosted cloud database so that all team members and CI workflows query against a consistent, synchronized data source.

## Consequences

- **Positives (What this makes easier):**
  - **Zero local database installation:** Developers and CI runners clone the repo and run the Go backend immediately with no local PostgreSQL service required.
  - **Zero query rewrite:** Because Supabase is native PostgreSQL under the hood, all existing SQL queries (`SELECT`, `INSERT`, `UPDATE`, `JOIN`) and connection pool configurations in `backend/main/main.go` and `backend/assignments/handlers.go` work transparently. If we ever migrate to self-hosted PostgreSQL or another cloud provider (e.g., AWS RDS, GCP Cloud SQL), no backend application logic needs to change.
  - **Unified file and relational storage:** Assignment file URLs and relational records are managed within the same cloud ecosystem, eliminating the need for separate cloud storage subscriptions.
  - **Centralized data visualization:** The Supabase Table Editor enables real-time inspection, manual test data verification, and fast schema validation.
- **Trade-offs (What this makes harder or rules out):**
  - **Network dependency:** Local backend execution requires an active internet connection to communicate with the hosted database instance. (Mitigated by keeping core domain logic, such as `GradeAssignment()`, completely decoupled from database access so unit tests run fast and offline).
  - **Secret management:** Connection strings and credentials must be maintained carefully in `.env` and injected securely into CI/CD secrets without exposing credentials in version control.
  - **Connection pool limits:** Supabase free-tier connection limits require using connection pooling (`pgxpool`) to prevent exhausting available connections.
